# XRM：删除旧 TUI 界面实现，基于组件重建 TUI，并重设计 CLI

> 本文件是交给 Codex 的执行任务，不是建议稿。以用户本轮九项 G5 反馈和五张截图为依据。
> 本轮目标：交付可操作的新组件库、新 TUI 全部页面、新 CLI 帮助与输出，以及真实终端验证；不能仅修补旧界面、拆分文件、安装工具或输出设计方案。

## 0. 任务判定与规则优先级

上一轮虽然报告了自动测试通过，用户人工使用仍发现基本输入控件、表单、信息区域、通知、模块可视化和 CLI 帮助不符合要求。本轮不是“再做一次 polish”，而是**重建 xrm 的人机界面实现层**。

授权你删除并替换旧 TUI 的页面绘制、弹窗、逐字段 Prompt、页面级输入拼接和相互交叉的事件处理代码。最终所有生产页面必须使用同一套组件、布局、焦点与状态模型，不能留下旧页面、新页面并行的两套产品。

“删除重写”是最终实现要求，不是让你先执行 `rm -rf src/tui`，破坏后再补。先识别边界、建立可回退的本地基线，再实现和切换，最终删除被替代的旧代码及构建引用。不是复制旧 app.cpp 到多个文件就宣称组件化。

保留：C++23、FTXUI、CLI11、xrm/xrmd 分层、独立 Xray-core、原生多文件 confdir、库存/方案/运行配置边界，以及不与新规则冲突的有效能力和测试。不要重写 xrmd，不迁移数据库，不更换 TUI 框架，不加入 WebView/HTML，不改成 libXray。

### 本轮明确覆盖旧约定的内容

| 事项 | 本轮唯一规则 |
|---|---|
| Profile 的 Edit | 是针对一个明确 Profile 的**模块编辑模式开关**，不是 Profile 元数据编辑器，也不是假想的整套 Profile 原子事务。 |
| Edit 关闭 | 该 Profile 的 Modules 为只读；Visual、JSON、外部编辑器及其他模块写入口都不能绕过。Profile 本身正常增删改查不以 Edit 开启为前提。 |
| Use | 必须可以取消；取消不自动停止核心、不清除保存目标、不影响模块编辑会话。 |
| 常用快捷键栏 | 取消主视图和底部常驻的整排操作提示；操作说明集中到统一 Help。底部只保留一个简短 Help 入口标识。 |
| 查看对象后的说明 | 显示在底部信息区，不再插在可选列表或日志正文中。 |
| 临时反馈 | 右上角、不抢焦点、自动消失的 Toast；不是底部永久留存的一句消息。 |
| Visual 模式 | 原生配置对象的语义化表单与集合编辑，不是要求填写 JSON，也不是通用 key/type/value 编辑器换名。 |
| 表单 | 同一表单内展示多个带标签控件，可来回编辑；不是填写一个文本框、Enter 后再换下一个字段。 |
| 交付范围 | 全部 TUI 页面与公共交互控件重建，并重设计 CLI 命令发现、分级帮助、错误和信息输出。 |

先读 AGENTS.md 和当前有效文档。对本轮 UI 语义冲突，以本任务为准，并同步修改 `docs/xrm-interaction-spec.md`、项目 Skill、当前使用说明和人工验收清单。历史审计保持历史性质，不改写历史结果。不得以旧文档为由恢复旧语义；也不得同时保留两套有效规范。

## 1. 输入、基线和安全边界

读取实际存在的：

用户这次的九项反馈是任务输入：

1. Logs 的日志正文、固定标题、调试状态和操作说明混在一起，难以辨认。
2. 订阅更新仍是底部文字，没有右上角自动消失的通知框。

4. Use 无法取消；Edit 被错误做成 Profile 字段编辑，而用户要的是 Modules 写入模式开关。
5. 各种输入框不能用方向键正常移动光标。
6. Modules Visual 应按 DNS 服务器、routing 规则等原生对象提供有结构的表单，不是任意 JSON 编辑。
7. 可视化集合操作不完整；新增用串行单字段提问，而不是多控件表单。
8. Group 的有限枚举用文本框输入关键词，拼错后表单退出。
9. 缺少真正复用的单选、多选、列表、树、文本编辑、弹窗等组件，页面靠局部代码拼接。

另外，CLI 截图中裸 `xrm` 和 `xrm server` 都返回同一条根命令提示。截图不能证明解析器没有子命令，但已经说明**当前上下文帮助与命令发现失败**。必须检查真实注册树和 fallback，不得只把那句提示写得更长。

先确认当前分支、工作区差异、执行路径、构建产物与当前源码的对应关系，避免验收运行到旧的 build/dev 或已安装二进制。发现版本错位要报告，但不能以此代替本轮明确要求的重写。

保护用户未提交改动和未跟踪文件，不执行覆盖性 reset/clean，不自行提交、推送或发布。允许在项目范围内修改相关源码、测试、文档与必要构建配置。

运行测试使用独立 xrmd socket、数据库、HOME/XDG、confdir、loopback fixture、端口和终端会话。不要使用截图里的真实订阅地址、节点、运行目录或生产实例；不要更改系统网络、TUN、防火墙、systemd 服务。清理仅针对本轮记录的资源，禁止宽泛 killall/pkill。

## 2. 工具与研究：沿用已安装能力，不重新堆插件

上一轮报告终端设计 Skill、项目 Skill 和 tmux MCP 已安装，但宿主是否发现 MCP 仍需验证。分别确认：文件存在、Skill 正文已读、宿主已发现、真实调用成功。不能把“直接 MCP 协议可调用”和“已通过当前宿主加载”混成一个结论。

优先使用已有终端 MCP；宿主未加载时，继续使用已经验证的隔离 tmux/PTY 路径，不为此停工或另装多个终端工具。Skill 必须服从本轮产品语义，不能套用上游默认导航。

本轮研究只服务于实现：

- **FTXUI 官方组件与项目锁定版本源码**：优先复用 Input、Checkbox、Radiobox、Dropdown、Menu、Button、Container 等已有能力，补齐 XRM 需要的组合控件。不能凭“GUI 通用组件”之名重新发明整个渲染/输入框架。

- **Command Line Interface Guidelines**：简明默认帮助、上下文帮助、人读/机器输出、错误、非交互和兼容性。
- **GitHub CLI 与 Docker 官方命令手册**：研究它们的分组命令、局部帮助、参数说明、示例和进一步发现路径。提炼设计方法，不复制与 XRM 无关的命令结构，不为研究去安装或启动 Docker/GitHub 服务。
- **Xray 官方全量配置文档**：所有原生字段、枚举、类型、条件和默认值的依据。为当前固定核心核对适用性，不能把最新文档自动当成旧核心全支持。

在执行记录中简要写明“参考了什么、采用了什么、没有采用什么”，不要交付几页工具清单代替界面代码。

参考入口见文末。涉及 Xray 配置前，必须打开全量文档的相关章节。文档无法确认时写“文档未提及，不能确认”，不能用模型记忆、社区模板或其他核心的字段补全。

## 3. 组件先行：不是逐页重画，也不是做一个通用 GUI 引擎

先建立服务于 XRM 的小型组件层和统一 Shell，再组合全部页面。

建议的职责划分如下，具体目录可按现有工程调整，不要求照抄名称：

```text
src/tui/
  app.*                 # 生命周期与组装，不承载所有页面业务
  shell/                # 导航、焦点域、底部信息区、Overlay 层
  components/           # 输入、选择、列表/表格、树、表单、对话框等
  state/                # 会话状态、编辑模式、草稿、异步结果状态
  actions/              # 当前上下文动作、可用条件、Help 元数据
  pages/                # 全部页面，由组件组合
  forms/                # 原生模块与领域对象表单
  adapters/             # DTO / 原生配置与视图模型之间的薄适配
```

必须遵守依赖边界：

- 基础组件不依赖 Xray RPC 名称、Profile ID 或具体页面。
- 页面声明组件和绑定业务意图，不自行实现字符插入、退格、光标或枚举解析。
- Render 不执行写 RPC、不改变草稿、不启动任务。
- 输入与异步动作通过明确的控制器/处理器更新状态。
- 组件生命周期稳定；不能每帧重建输入组件，导致光标、选择区、滚动和焦点丢失。
- CLI 与 TUI 可共享领域适配和结果模型；TUI 不拼 shell 命令调用 CLI，也不解析 CLI 人读输出。
- 不引入新的通用插件框架、复杂 DSL、事件总线体系或数据库模型来替代必要的简单 C++ 类型。

### 3.1 必须落地的组件能力

| 组件族 | 必须支持的能力 | 至少一个真实使用位置 |
|---|---|---|
| TextInput / SecretInput / NumberInput | 正常光标编辑、校验、只读/禁用、错误不丢值；秘密默认遮蔽 | Profile 重命名、订阅表单、地址/端口 |
| TextArea / CodeEditor | 多行编辑、上下左右、行首尾、滚动、选区/复制粘贴的已实现边界；JSON 错误定位 | Modules JSON、节点高级编辑 |
| StyledText / ReadOnlyText | 分段强调、换行、长文本与受控滚动；与可编辑值分离 | 底部详情、错误详情、日志 |
| Select / RadioGroup | 在有限合法值中选择；未知旧值可识别，不能被默默替换 | Group 类型/策略、模块枚举 |
| Checkbox / Toggle / MultiSelect | 布尔、多个成员、多条件选择；显示可读标签 | 组成员、订阅设置、原生数组字段 |
| List / Table / ScrollViewport | 表头、列宽策略、ID 稳定选中、分页/滚动、空/加载/离线状态 | Profiles、Subscriptions、Nodes、Core |
| Tree / SectionList | 折叠层级与选中分离、键盘可达；用于真实层级，不把 JSON 树冒充语义表单 | 原生嵌套配置/分组段落 |
| CollectionEditor | 新增、查看、修改、删除；有顺序语义时支持重排；子编辑取消不破坏父草稿 | DNS servers、routing rules、组成员 |
| Form / FormField / Button | 同屏多字段、标签、约束、字段错误、明确提交与取消、滚动与焦点顺序 | 订阅、Group、DNS/routing 子对象 |
| Dialog / Confirm / HelpOverlay | 焦点限制在当前层、关闭后恢复、嵌套不穿透、内容可滚动 | 编辑、删除确认、Help |
| ToastHost | 右上角浮层、过期、去重/有界队列、无焦点、副作用结果关联 | 订阅更新、保存成功/失败 |
| LogViewer | 纯日志正文、稳定历史滚动、跟随/暂停、长行/多行、元数据分层 | Logs |
| InfoPane / StatusBar | 当前对象、模式、详情、连接状态、路径；不混入选项或快捷键长列表 | 所有页面 |

“富文本框”在这里是终端内分段样式展示与可用的多行文本编辑，不要求制作网页 WYSIWYG 编辑器，也不能把格式标记写进 Xray JSON。

复用 FTXUI 的已有能力，缺少的才做适配或组合。不能声称 FTXUI 自带所有这些高级控件。不要造一个没有调用方的空组件目录，然后页面继续拼字符串。

### 3.2 组件完成的判据

建立一个独立、无需 xrmd 的组件展示/测试程序，作为开发测试目标，不必成为用户生产命令。

组件在接入页面前，先在该程序验证正常、只读、禁用、错误、长内容、中文、窄屏、焦点和鼠标支持边界。常用控件必须被多个实际页面复用，并有组件测试。组件展示程序通过不等于页面集成完成。

为所有组件统一：文字与强调层级、内外间距、标签对齐、聚焦/只读/禁用样式、选中状态、错误显示、滚动、提交和取消行为。默认不要求 Nerd Font，不以颜色作为唯一状态标识。

## 4. 输入与焦点：方向键首先属于真正的控件

保留已确认的主导航范式：TopNav → 可选 SecondaryNav → Content；Tab/Shift-Tab 只在当前层切换；Enter 进入一层并消费；Esc 只退一层。非 Content 不执行内容动作，不恢复数字键、`[]` 或方向键绕过主导航。

**不要把该规则误解为表单控件不能使用 Tab 或方向键。**

- Content 内打开表单/对话框时，形成局部焦点域，Tab/Shift-Tab 在当前表单控件间移动，不切顶层页面。
- 文本框聚焦时，左右移动光标；多行框上下移动行位置；Home/End、Backspace/Delete 正常工作；文档首尾及选区操作按统一组件定义实现并在 Help 说明。
- 单行输入框里的上下键不能泄漏到背景列表；多行编辑中的 Enter 是换行，不是保存或导航。
- 普通可打印字符，包括 q、e、u、p、?、空格，按所属控件处理，不触发背景动作。
- 表单采用明确保存/取消按钮和统一保存动作。不要继续把每次 Enter 作为“销毁当前输入框、换下一个字段”的串行提问。
- F1 作为所有上下文的统一 Help；非文本上下文保留 `?` 作为同一 Help 动作别名，文本框里的 `?` 必须仍可输入。底部只显示一个 Help 标识，不新增另一套命令面板。
- Help 打开后原表单与光标保持，关闭后回到原控件；帮助/确认层的 Esc 不穿透到页面。
- Toast 不参与焦点遍历，不吞掉按键。

测试 UTF-8 中文和混合文本的插入/删除，不能按字节删坏字符。核对终端组合字符、宽字符的显示与编辑边界，不靠“支持 Unicode”一句话代替测试。

所有输入相关按键必须在真实 PTY 里验证。检查上层是否先吞掉事件，不能只给 Input 加一个 cursor_position 就宣布修复。确保终端输入模式不会让 Ctrl-S 被流控吞掉，并在退出后恢复终端状态。

## 5. Shell：内容、信息、操作帮助、临时反馈彻底分区

建立统一布局职责：

```text
顶部：顶级导航；需要时有二级导航
主体：当前任务的列表、日志、原生表单、图表或编辑器
底部：当前对象详情 + 运行/查看/选用/编辑状态 + 必要路径与模式
帮助：一个可发现入口，打开统一上下文 Help 浮层
通知：独立 Overlay 层，右上角 Toast，定时消失
```

主体可以有真实业务表头、字段标签和必要的就地校验，但不要把操作说明、架构宣言、调试游标或选中项附加说明混在列表项/日志中。

### 5.1 删除常驻快捷键长条

删除类似以下占据主体或底部的长条：

- `↑↓ Move  Enter View  u Use  e Edit ...`
- `p Pause  ↑/↓ history  r refresh  Server buffer remains active`

操作及键位放进 Help。Help 按当前页面、焦点、对象和模式显示有效动作、目标、快捷键及禁用原因；其数据与真正执行的 Action 定义来自同一处。

这不意味着隐藏表单的 Save/Cancel 按钮或选择控件的标签。它们是正在完成任务的控件，而不是全局快捷键说明条。

### 5.2 底部信息区

Profiles 的 Enter/View 更新底部详情，不在主体列表后附加 `Plan: ... Core: ... Sources ...` 等解释段落。光标项、查看对象、Use 对象、Edit 对象、运行对象分别建模；展示目标必须有名字/身份，不能让用户猜详情对应哪行。

用分区、对齐和简洁标签表达状态，不在 Toast、底部两行、主视图三处重复同一串 Viewing/Using/Running。

底部详情有明确高度预算和长内容处理；80×24 下不能无限扩张而淹没主体。需要完整长信息时可在底部详情的受控展开/局部滚动中查看，沿用局部焦点规则，不创建第二套页面导航。已在主体显示的业务列，不必全部再重复一遍。

“信息放底部”指全局状态、选中/查看对象说明、路径和模式；不意味着把日志正文、表单字段、业务列表也搬到底部。真正需要输入或阅读的业务内容仍在主体。

空状态、离线、加载、失败和过期分别建模。未知不是零，运行进程不是网络可用。恢复连接不能抢焦点、清稿或自动重放写动作。

## 6. Profile：纠正 Use / Edit，不再照上一版错误实现继续改

至少区分以下状态，具体类型自行实现：

- 当前光标项；
- viewed_profile_id；
- used_profile_id，可为空；
- module_edit_profile_id，可为空；
- 按 Profile/模块来源身份绑定的草稿；
- 后端报告的运行实例与实际目标。

不要用一个“current profile”或无归属 bool 代替所有状态。

### 6.1 Use 可取消

在 Profiles 上，对 P 执行 `u`：

- 当前 Use 不是 P：设为 P。
- 当前 Use 已是 P：清除 Use。

这是同一动作的明确切换，不另加一套清除命令。Help 根据上下文显示“使用此方案”或“取消使用此方案”。

Use 切换只改变后续操作的会话选用对象，不自动连接、停止、清理运行配置、修改保存目标或关闭 Edit。取消后明确显示 Use 为空。需要 Use 的运行动作此时禁用并给原因，不能悄悄回退到光标项、View、上次使用或正在运行的方案。

CLI 原有显式目标参数不依赖这个 TUI 会话状态。

### 6.2 Edit 是模块编辑模式，不是 Profile 元数据表单

`e(P)` 的动作名称应清楚表达“允许/结束编辑 P 的模块”。每个 TUI 会话只维持一个明确归属的模块编辑上下文，不能同时有两个混淆的活动编辑目标。

开启 P 的 Edit 时，使 Modules 的查看目标明确指向 P，避免“正在编辑 P、表单却显示 Q”。这可以更新 View，但不得改变 Use 或 Run；必须在契约中固定此行为。开启本身不保存、不创建整个 Profile 总草稿，也不自动生成/写入模块。

关闭 Edit 或切换编辑目标前，处理该目标未保存草稿：保存、放弃、继续编辑。保存失败则保留模式、输入和目标，不能先关 Edit 再报告失败。

Edit 关闭时，Modules Visual 与 JSON 都可查看、滚动、复制，但所有模块写入口必须被同一门槛禁止，包括字段修改、集合增删改重排、included 更改、预设保存、从外部编辑器导入以及其他实际修改既有模块 Source 的动作。不能只把某个按钮变灰，后台仍可调用模块写动作。

运行配置视图永远只读，开启 Edit 也不改变这一点。保存 Source 不隐式 Use/Connect/Apply/Restart。

Profile 创建、查看、重命名、复制、删除等正常管理不依赖模块 Edit；删除/切换有草稿的对象仍要明确处理草稿。节点库、订阅库、Profile bindings 等独立资源按各自动作合同管理，不能因为 Edit 关闭就把整个程序锁死。

新建/克隆 Profile 初始化资源与修改既有模块是不同领域动作，要清楚区分，不通过宽泛的“禁止一切写操作”破坏 CRUD。

这是**TUI 的编辑模式保护**，不是新增权限系统或 daemon 全局写锁；不要让 CLI 必须先在 TUI 开 Edit 才能执行显式配置命令。

## 7. Modules Visual：按原生语义构造表单，不是泛型 JSON 壳

Visual 的用户任务是“添加一台 DNS 服务器”“编辑一条 routing 规则”“选择一种策略”“管理一个原生数组中的对象”，不是“新增一个键，填写类型，再粘 JSON”。

### 7.1 唯一配置依据与原生边界

先读取：`https://xtls.github.io/llms-full.txt` 中当前模块相关部分。记录实际采用的字段路径、类型、允许值、条件、默认值与文档依据，并核对固定核心适用性。

- UI 模板只是原生结构的交互映射，不是另建 XRM 配置语言。
- 有限枚举使用选择控件；布尔使用复选/开关；集合使用列表和 CollectionEditor；自由字符串才使用文本框。
- 表单提供“未设置/使用默认”与“显式写入”的区别，不把所有默认值强行写入文件。
- 必填/可选、条件字段和互斥关系只按官方依据实现，不能猜。
- 未知字段和暂未支持的类型必须保留，不因表单提交被删除、转换或默认覆盖。
- 不给原生规则/对象虚构 `enabled`、`type` 等便利字段。UI 临时状态不得序列化进 Xray 配置。
- 策略组与 routing.balancers 的既有映射、节点库存与运行片段的边界继续保留，不虚构独立原生顶层 group 模块。

### 7.2 DNS 服务器：必须做成完整集合与多字段表单

DNS Visual 至少应能让用户完成：服务器列表浏览、添加、查看、修改、删除，以及原生顺序有意义时的重排；并保留已支持的 hosts 和其他设置。

添加/修改同一台服务器时，打开一个包含多个控件的 Form，而不是连续弹出单字段 Prompt。地址/端口、条件列表、枚举和布尔项按实际官方结构使用对应组件。字符串与对象两种原生表示要正确映射，不能无条件改写原数据形态或丢失高级字段。

用户在提交前能返回修改前面的任何字段；某字段错误只标记该字段并保留全部输入。提交对子集合草稿生效，最终保存到 Source 的边界必须明确，不能混淆“加入当前草稿”和“持久保存模块”。

### 7.3 Routing：规则是可管理的有序对象，不是 JSON 文本块

提供可阅读的规则列表和规则表单。规则应能查看、添加、编辑、复制、删除、重排；因为规则顺序可能影响匹配，不得擅自排序。

表单按“匹配条件—目标—高级项”组织，使用真实字段支持的组件。已存在的目标或有限类型用选择器；列表值用可管理的集合；条件之间的组合关系必须按官方文档呈现。

不要让用户记忆一个有限关键词；也不能把所有字段限制成你猜测的几个常用值，悄悄破坏合法高级配置。涉及组或 outbound 引用时验证引用与作用域，不能按显示名称随意拼 tag。

### 7.4 其他模块不是占位符

对当前项目已支持的全部原生顶层模块和已暴露子配置建立覆盖矩阵：哪些是单值表单、哪些是对象列表、哪些是嵌套区域、哪些是高级 JSON；映射到真正的新组件。

DNS/routing 是强制验收样例，不是只做这两个后宣布全部完成。其他原有页面、模块和节点高级编辑也必须迁移到新组件；不能留下旧 Prompt 或偷偷退化成只能查看。

对于不能可靠表单化的高级字段，可以明确由 JSON 模式管理，并保留往返数据。不能把“高级 JSON 可用”当成常规 DNS/routing 任务没有 Visual 表单的借口。任何支持缺口必须明确列出，不能写成完整支持。

### 7.5 Visual / JSON 共用草稿

Modules 继续使用一个全宽工作区域，F2 在 Visual 和格式化 JSON 之间切换，不做左右两个同时竞争焦点的编辑器。

使用一个权威 DraftSession，内部按需要保留原始文本、有效语法树和脏状态；不是两份互相覆盖的数据模型。

- Visual 改动反映到相同草稿的 JSON。
- JSON 合法改动再切回 Visual 时正确回显。
- JSON 非法时保留文本、光标和错误位置，不强行切 Visual 或重置。
- Visual 只修改其负责的字段，保留未知字段、原生类型和顺序语义。
- 打开查看、格式化展示、切换视图，不得自动保存 Source。
- 表单确定、模块保存、运行发布分别表达；不能一个按钮暗中做三个动作。
- Source 保存仍走现有 daemon/原生文件边界，不从另一套 UI 数据模型重生成整套 confdir。

## 8. 统一表单、Group 与所有编辑窗口

订阅添加/修改、Profile 元数据管理、核心登记、Group、节点、Modules 子对象、XRM 设置等，均复用 Form 和组件层。

有限选择必须来自真实支持集合：Group 类型/策略不能让用户手写枚举词；成员用可搜索的列表/多选；已存在的 Profile/核心/目标引用使用有身份的对象选择器。列表里的名称只是展示，提交绑定稳定 ID。

已有配置中遇到未知值时，显示“不受当前可视化支持的已有值”，保留原值或引导明确处理，不默认选第一项覆盖。

复杂配置可以有“基础/高级”折叠区域，但默认不能退化为一问一答向导。新建、查看、修改、删除都要实际可达，不要只有添加。

所有保存失败：字段无效、JSON 无效、RPC 拒绝、daemon 断开、超时结果待确认，都必须保留草稿与上下文。字段错误放在字段附近，必要时同时 Toast；不能只发一个消失的错误通知，然后关闭表单。

保存成功后才推进持久基线。取消/关闭有未保存改动时按统一规则确认，不能在不同页面一个保留、一个静默丢弃。异步响应按对象和操作身份回写，不能覆盖已经切换到另一个对象的表单。

不要为统一界面虚构跨 Profile、节点库、模块文件的一次原子事务；实际保存边界不同就诚实表达。

## 9. Logs：正文只负责日志，固定说明从正文移走

重建 LogViewer，移除混排在日志中的 `Viewport top: ...`、`cursor ...`、操作说明等 UI 固定文本。这些必要状态进入底部信息区，开发调试信息不常驻普通视图。

- 主体用于实际日志记录，不为每条短记录无条件插空白行。
- 时间、级别、来源和消息有可辨认的层级；重复元数据弱化，消息为主体。
- 长行和多行记录采用明确的换行/续行缩进与滚动策略，不能让续行看起来像一条无来源的新记录。
- 不假设一次 IPC/stdout chunk 就是一条日志；核对现有数据结构和换行边界，避免串行、截行或错误添加序号。
- 只对能够可靠识别的时间/级别做结构化；未知格式原样可读，不丢行。
- 不因消息正文含“failed”就把原本 Info 级别擅自改成 Error；可以突出文本，但不能伪造来源事实。
- 简洁显示不能损失排障能力：原始消息、完整路径、完整时间和原始来源仍可从明确的详情/原始查看入口获得；排障信息与屏幕默认摘要分层。
- 原始输出中的终端控制序列不能任意影响窗口/剪贴板；按现有安全策略受控显示，不把日志当可信终端指令执行。

跟随、暂停、历史位置、新增数量、丢弃/截断、连接状态在底部表达。暂停期间新日志到来不拉回底部；恢复跟随有明确动作。后端有界缓冲与截断事实不能因为“变好看”而被隐藏。

Logs 的动作仅与日志阅读有关，c/d 等不允许触发运行生命周期。截图中的健康检查失败是日志数据，不是本轮借机调整真实代理、健康检查配置或订阅的授权。

## 10. Toast：右上角浮出并消失，不替换成另一条 footer

实现可复用 ToastHost，绘制于 Shell Overlay 层，位于内容区域右上角，不遮挡导航与底部必要信息。

- 与主体布局独立；出现/消失不插入列表行、不挤动主内容、不改变焦点和输入光标。
- 明确表现成功、信息、警告、错误；文字中带动作和目标，不只写 Success。
- 使用统一且可测试的过期策略，例如普通成功/信息 3 秒、警告 5 秒、错误 8 秒。它们是本项目 UI 默认值，不是 Xray 配置项。
- 成功 Toast 自动消失；错误 Toast 也自动收起，但错误在相关字段/对象状态或有界通知历史中仍可找回，不丢失关键失败事实。
- 有上限的队列/同时显示数量，重复刷新错误合并；不能堆满整个屏幕。
- 订阅刷新只在最终完成结果确认后报告成功；部分失败、失败、取消、结果未知分别表达。
- 通知绑定操作及对象，不把上一个页面的“节点不在列表”永久留在 Logs；页面局部陈旧消息有明确过期/撤销规则。
- 80×24 下按字符宽度折行和约束尺寸，不依赖网页像素、不假定能做透明玻璃效果。
- 动效最多是克制的出现/消失和必要忙碌反馈，不阻塞事件循环，不强制为了“好看”延迟操作。

对截图中的订阅更新任务，必须真实操作并展示通知出现、到时消失、后台状态更新以及焦点不变。

## 11. 全部页面迁移与布局要求

保留 Overview / Profiles / Modules / Subscriptions / Nodes / Logs / Config 的能力入口，全部由新组件组合；核心、Geodata、组、外部编辑器、设置等现有子任务不丢失。

- Profiles：列表只呈现适当的对象列；Enter 的说明在底部，Use 可切换取消，Edit 按新语义。
- Subscriptions：使用有合理列宽的 Table；不要把 Name 扩成巨大空白后，把 Nodes/Result/Profile 挤到最右侧。更新、编辑、绑定、暂停/恢复、移除都有一致入口。
- Nodes/Groups：光标、保存目标、运行目标清楚区分，组选择与表单控件真正可用。
- Modules：全宽 Visual/JSON、明确 Source/Runtime、模式保护、语义表单和完整集合操作。
- Logs：独立日志阅读控件与底部状态。
- Config：核心及资源管理、XRM 设置采用相同表单/列表/选择器，不沿用特殊 Prompt。
- Overview：结构化呈现实际运行与资源情况，不能把后端字段逐行 dump，也不反复堆设计说明。

少数据时留白是允许的，不为填满屏幕增加空卡片、标语或架构说明。宽屏应改善可读性和信息组织，而不是无上限拉宽某一列。窄屏有明确列优先级、布局与滚动策略，不靠截断整句掩盖设计问题。

统一 80×24 和 120×40 布局，并检查一个更宽尺寸。小于最小尺寸给保护视图，恢复后保持草稿和焦点。不要改字号或要求用户最大化终端来回避问题。

## 12. CLI：真实分级命令帮助，不再输出一句根提示

保留 CLI11 和现有有效命令/参数/机器接口，重建注册描述、默认帮助、上下文诊断与人类输出。

不要写一个新的手工字符串列表来冒充命令系统；帮助应从实际注册树与少量维护的说明/示例生成。命令分组和术语一致，仍可以保留现有 connect/disconnect 等顶层便利命令，不能为了形式统一破坏脚本。

### 12.1 默认与分级帮助

明确实现并测试：

- 裸 `xrm`：程序用途、Usage、按任务分组的真实命令及一句说明、少量起步示例、下一层帮助入口；不自动进入 TUI、不访问 daemon。
- `xrm server`：只展示 server 层的 Usage、真实子命令及示例；不能退回同一条根提示。
- `xrm profile`、`xrm node`、`xrm config` 等分组命令：同样显示当前层的帮助，而不是全部命令 dump。
- 任意层 `-h/--help`：显示该层完整、可读的参数、选项、默认行为与示例。
- 叶命令缺必需参数：指出具体缺什么，给该叶命令的用法与合法示例，返回明确的非零退出码；不回根提示。
- 未知子命令/选项：报错并指向当前层的可用项；可做有限纠错建议，但不能自动执行猜测命令。
- 仅请求帮助/版本时，不尝试连接 daemon，不创建数据库或修改配置。

可增加与注册树一致的 `xrm help <命令路径>`，但必须真实实现所有路径解析，不能只做根 help 的别名。默认无参数帮助、显式帮助、参数错误、JSON 模式下错误的流与退出码须明确区分，并兼容已有机器约定；不要让 --json 失败时混入普通帮助大段文字。

所写每个示例必须来自真实命令，不虚构 `server start` 等未经实现的动作。核对 CLI11 锁定版本的子命令回调/required 行为，不能依据最新文档写不存在的 API。

### 12.2 输出按任务组织

- 列表：表头、关键状态、可引用 ID、清晰空结果、合理列宽；不在机器输出中截断标识。
- 详情：分组字段，明确所属对象/范围；默认不 dump 原始 RPC JSON。
- 创建/保存：告知哪个对象发生什么变化、身份/位置与是否影响运行。
- 连接/停止：只报告已确认状态，不把启动进程等同于代理连通。
- status：区分全局运行上下文和指定 Profile 的保存状态，不能把无运行实例显示成全部 Profile 没保存。
- 错误：操作、对象、原因、可执行的修复方向；不编造 systemctl 服务名或不存在的参数。
- 进度与最终结果分离；结果成功但附加查询失败时，不把已完成的变更误报为未执行。

必要时补齐 CLI 的真实任务缺口，但不先发明一个新的庞大命令树。新增命令必须使用已有后端能力、有 help、有错误处理、有测试。CLI 与 TUI 共享领域语义，不强求二者有相同交互手势。

### 12.3 保留机器和管道能力

保留 --socket、显式目标引用、既有 --json schema、可引用 ID、stdout/stderr 分工和已承诺退出码。必要的有意变更必须明确记录，不能暗中破坏。

默认 CLI 保持非交互，不用串行问答来补缺参；非 TTY 不等待输入、不发屏幕重绘/动画控制序列。按现有契约处理颜色关闭与 TTY 判断。

保留上一轮已修复的 stats --watch 逐条及时输出、daemon 中途断开错误报告、Ctrl-C 正常退出等行为。分别测试“输出消费者关闭管道”和“与 daemon 的连接断开”，不能通过全局忽略 SIGPIPE 掩盖错误或无限重试。

普通输出、日志和帮助默认不泄漏凭据；已明确授权的原始导出契约另行核对，不能借脱敏之名静默改机器接口。

## 13. 实施顺序：组件完成后必须继续完成页面和 CLI

按下列阶段推进，同一次任务中持续实施，不在阶段结束时只写“下一步建议”。

### A. 基线与新契约

确认当前产物和代码，读取现有文档与必要官方资料；记录本轮九项反馈；更新唯一交互契约及项目 Skill。明确哪些旧期望被新要求替代。

### B. 组件与 Shell

实现/组合基础输入、选择、表单、列表、树、对话框、Help、InfoPane、Toast、LogViewer；用无需 daemon 的展示程序验证。

首先证明文本光标可用、多字段表单可用、有限选项可选、对话框焦点不穿透、Toast 不抢焦点。不能跳过此阶段直接逐页复制处理代码。

### C. 一个完整纵向任务

用新组件打通：Profile 选择/取消 Use → 开启模块 Edit → DNS/routing 的真实 Visual 表单 CRUD → F2 JSON 往返 → 保存/失败恢复 → 关闭 Edit 后只读 → 显式运行 → Logs。

这条任务必须真正使用新状态与控件，不能继续调用旧 Prompt 作为后备。

### D. 全页面与 CLI

完成全部剩余页面/弹窗/编辑器、原生模块表单覆盖、订阅和 Group 完整生命周期，重设计 CLI 帮助/错误/输出。对照旧能力矩阵防止漏功能。

### E. 删除旧实现并完整回归

删除被替代的旧页面绘制、逐字段提示器、各处自制输入、旧 footer 操作栏、旧事件 fallback、构建引用和无调用路径。最终只保留一套可运行的 TUI。

迁移中可用独立开发目标比较，不提供生产旧/新 UI 切换开关。可保留经验证的纯业务适配/状态算法，但要明确复用原因，不能借此把旧 UI 搬到新目录。

同步更新因产品语义变化而过期的测试与快照；保留原生配置、机器接口、无隐式副作用、草稿不丢失等不变量。不能删失败测试、跳过回归或批量重录快照掩盖问题。

若并行开发，先固定公共组件接口与契约，再按文件所有权分工；各子任务不能自行发明快捷键、保存或通知方式。最后由一个集成阶段统一验收。

## 14. 强制验收：不以断言数量代替可用性

建立状态/组件测试、当前屏幕格与样式检查、真实隔离 PTY 流程三层验证。终端 MCP 用于真实操作观察，关键回归还必须能从仓库命令重复执行。

### R1：组件是真实复用

给出组件→页面使用矩阵。公共 Input/Form/Select/Dialog/InfoPane 等有真实调用方。检索确认页面不再各自实现退格/光标或手写枚举提示链。不能只有空壳接口与一个 Demo。

### R2：输入框

单行和多行、英文和中文混合输入，在中间移动光标、插入、删除、换行、Home/End、Tab/Shift-Tab 切字段；验证结果字符串和屏幕光标。表单里输入 q/u/e/p/? 不触发页面命令。保存失败仍保留文本、光标、选择和目标。

### R3：焦点与 Help

顶级/二级/内容/表单/确认/Help 每层 Enter/Esc 不穿透。F1 可从输入框打开同一 Help 并返回；? 在输入框里是文本。主视图与底部没有整排常用操作提示，只有单一 Help 入口。帮助列出的动作和实际权限相符。

### R4：Profile 与模块只读

P Use→再次 u→Use 为空，不影响已有核心或保存目标。P 开 Edit、Q 未开 Edit 时目标不串；P 模块可改、Q 模块只读。关闭/切 Edit 遇未保存稿有明确处理；失败不丢稿。Edit 关闭时 Profile 重命名/创建等仍可用。模块预设、included、JSON/外部编辑器不能绕过只读。

### R5：查看信息区域

Profiles 按 Enter，详情只在底部对应区域更新，不向列表插入 Plan/Core/Sources 说明。光标、View、Use、Edit、Run 不同对象时可识别。Subscriptions 表格在宽屏不把信息挤到两端；80×24 必要信息与完整帮助可达。

### R6：Toast

本地订阅 fixture 更新后右上角出现真实结果通知，按规定时间消失，内容行位置/焦点/光标不变。覆盖失败、部分失败、重复错误、多通知上限与窄屏。定时逻辑用可控时钟或有界等待，不堆长 sleep。表单错误不会随 Toast 消失而丢失。

### R7：Logs

当前日志正文区域没有 UI 的 Viewport/cursor/操作说明；多行与长行边界清楚。可靠级别保持原值，未知格式可读。暂停后新日志不抢位置，恢复跟随有效，截断/丢弃/断连在信息区可见。不得只搜索 scrollback 中曾出现过的字样。

### R8：真正的 Visual

不用 JSON 完成 DNS 服务器与 routing 规则的新增、查看、修改、删除和适用的重排。新增是同一多字段表单；能够回头改第一个字段，有限项由选择器给出。表单错误不会退出。Group 类型/策略不用手写关键词，成员多选可用。

### R9：原生数据与草稿往返

Visual→JSON→Visual 保持相同配置语义；原先存在的未知字段、合法不同类型、数组顺序不丢。只改一个字段不重生成整套 confdir。非法 JSON 留在编辑器；只读模式切换不写源。保存不自动运行。

### R10：CLI 层级帮助

分别捕获 `xrm`、`xrm server`、`xrm profile`、`xrm config`、实际叶命令 --help、缺必需参数、未知子命令/选项的 stdout/stderr/退出码。检查每一层只给相关信息，有真实可执行示例，不再同一句根提示。daemon 不存在时这些 help 仍可用且无状态变更。

### R11：CLI 输出与回归

列表、详情、空结果、创建、保存、连接、停止、失败，覆盖人读/非 TTY/--json；watch 及时 flush、Ctrl-C、daemon 中断、消费者关管道分别验证；保证不重现上一轮已修复的 SIGPIPE/缓冲问题。

### R12：全任务、尺寸与真实核心

所有七页及已有子功能覆盖；带未保存草稿在同一进程中完成 80×24→120×40→更小保护尺寸→80×24，验证恢复。检查一个宽屏布局。用批准的固定真实 Xray 和 loopback fixture 验证关键配置及流量，不用 fake-core 代签。

固定核心如沿用上一轮 v26.9.9，应核实实际二进制版本与摘要，不假定路径仍存在。未验证项写明 BLOCKED/SKIP，不能把配置检查通过写成全部协议或真实远端连通性通过。

每个关键场景同时观察屏幕和事实：草稿、持久数据、RPC 写调用、运行状态及必要的文件差异。测试报告中的大量断言不能证明信息清晰，必须展示有代表性的最终当前格和按键轨迹。

## 15. 交付与禁止“完成”的条件

交付必须包括：

1. 实际的新组件、全部 TUI 页面、CLI 帮助/输出实现与相关测试。
2. 已删除/替换的旧 UI 路径清单，以及旧能力如何保留的映射。
3. 更新后的唯一交互契约、项目 Skill、使用帮助与 G5 人工清单。
4. 执行记录：构建产物、研究与工具依据、组件复用矩阵、模块表单覆盖矩阵、测试命令/结果、CLI 实际输出、关键当前格与轨迹。
5. 一个真实可用的隔离体验入口：启动命令或仓库脚本、测试对象、清理方式；不把用户引向生产实例。
6. 工程验证状态与仍需用户人工 G5 复验的部分，分开报告。

以下任一情况存在，就不能宣称本轮完成：

- 只给旧界面加边框/配色，或把大文件机械拆开。
- 组件目录建了，但主要页面仍使用自制 Prompt/输入代码。
- 保留两套焦点、页面实现或新旧 UI fallback。
- Edit 仍是 Profile 元数据编辑器，或 Modules 默认可改。
- Use 无法取消，或取消后暗中换用其他方案。
- 底部仍是满排快捷键，或普通通知依旧只留在 footer。
- Visual 仍要求用户手写 JSON/有限枚举词，集合只支持添加。
- 输入光标、表单返回修改、失败保留草稿未实际验证。
- CLI 分组命令仍退回根级提示，帮助示例不存在。
- 只完成组件 Demo、DNS/routing 样例或几个截图，没有迁移全部页面。
- 以“自动测试通过”“Skill 已安装”代替用户要求已经实现的证据。

不要替用户把 G5 标记为 PASS。若任务因环境/权限受阻，说明已完成、未完成和恢复步骤，不伪造；但不能因为任务大就只停在计划或给用户一份未执行的建议。

**现在开始：核对当前代码和产物 → 更新新契约 → 组件与 Shell → 全部页面/CLI → 删除旧实现 → 真实终端与回归验收。**
