## 五、实现统一动作语法，消除交叉事件路径

以下是必须满足的不变量：

- TopNav / SecondaryNav / Content 分层处理；Tab、Shift-Tab 只在当前层切换。无二级导航的页面直接从 TopNav 进入 Content。
- 导航 Enter 只进入下一层并消费事件；同一次 Enter 不能顺便执行下一层动作。
- Esc 一次只关闭或返回当前一层。输入框、编辑器、弹窗优先拥有输入；导航层不能执行内容命令。
- 保留 TopNav 的 q 退出语义；文本输入中的 q 是文本，不是退出命令。退出 TUI 不停止 xrmd 或正在运行的核心，停止必须是独立显式动作。
- 不恢复数字键、`[]` 或方向键绕过既定顶级/二级导航。Content 内列表和编辑控件按上下文使用方向键。
- 移除 Content 中的跨页通用连接/停止回退分支。Logs 上 c/d 不得操作核心；Profiles 上合法的复制/删除键也不得顺带落入运行分支。
- `?` 等帮助入口的生效范围必须明确；输入控件需要输入的字符应归输入，不得被全局快捷键抢走。
- 同名业务动作语义一致；相同按键可以在不同明确上下文做不同动作，但不得存在一个上下文内的歧义、隐藏回退或多次执行。

建立一个轻量、明确的动作定义与分发机制，使当前上下文的按键执行、帮助和可用性来自同一份定义。可以使用 C++ 枚举、描述表与局部处理器，不要求引入通用插件框架或宏 DSL。

动作需绑定对象身份和作用域，不依赖保存时可能已经变化的列表索引。异步回调不得把 A 对象的结果应用到当前 B 对象，不得抢走用户焦点。刷新保留合理的高亮、滚动、查看对象和草稿；对象被删除时明确降级。

帮助不必挤下全部动作：底部显示当前高频且关键的动作，完整上下文帮助提供其他动作。执行来源与帮助来源必须一致。破坏性或运行副作用不能只藏在未提示的单字母快捷键中。

迁移某页面后删除或失效其旧事件路径，不保留两套都能触发的“兼容操作方式”。

## 六、真正完成编辑与状态模型，不用标签掩盖缺失

### 6.1 Profile

View 是查看；Use 是选择会话后续操作使用的 Profile，不启动核心、不建立编辑稿；Edit 必须进入一个真实、有目标、有字段、有保存/取消边界的 Profile 编辑流程。

I-05 不能通过改名、删除一句提示或继续显示 `edit context` 糊弄过去。核对现有 profile.get/save/rename 等合同，定义该编辑流程实际管理哪些字段，打开可编辑内容，并明确草稿属于哪个 Profile。进入编辑不会隐式 Use，保存也不会隐式 Use、Connect、Apply 或 Restart。

编辑事务范围必须真实：不得把独立节点库、各个原生模块文件和 Profile 元数据虚构成一次能原子保存的总事务。Profile 草稿只覆盖后端实际能够安全保存的范围；模块有自己的草稿和保存边界，界面要清楚表达。必要的跨资源步骤应说明已完成/未完成项，不冒充原子成功。

核对 A 正在运行、B 正在 Use、C 正在查看/编辑的情况。动作的目标必须明确，不能仅凭一个含混的“当前方案”字段决定写入对象。

### 6.2 全部编辑器

统一 Profile、模块、节点、组、订阅等编辑体验中的生命周期规则，而不是强迫它们使用同一个后端事务。

- 草稿与已保存值分开；记录目标身份、修改状态和错误。
- JSON 解析失败、字段校验失败、RPC 拒绝或断连后，保留当前文本/字段、光标和编辑上下文，允许继续修正。
- 保存成功才推进已保存基线；失败不能无条件关编辑器或从服务端覆盖当前输入。
- 有未保存内容时，Esc、切对象、切模式、离开页面等路径都需按契约处理；允许保存、放弃或继续编辑，不静默丢稿，不二次穿透。
- Modules 保留全宽单视图；F2 的 Visual/JSON 共用同一份草稿。非法 JSON 无法进入 Visual 时留在原处并说明原因，不重置内容。
- 外部编辑器失败、取消或返回非法内容也要保留可恢复输入，并正确交还终端控制。
- 检查 CLI/TUI 并发修改：能力允许时检测过期来源；不得虚构版本控制或事务保证。最少要识别能够确认的冲突，说明未验证边界。

### 6.3 服务状态与数据状态

分别表达：尚未加载、加载中、成功且为空、成功且有数据、刷新失败但有旧缓存、没有可用数据、daemon 不可达。库存未知不是零；无统计数据不是零流量；核心进程运行不是代理流量已经验证。

daemon 不可达时不得进入假首用或把库存清零。已有缓存可以继续只读展示，但必须标明过期和最后成功状态；无缓存明确不可用。全局连接状态、实际 socket 和恢复提示放在合适的底部区域，主体只表达其业务数据是否可用。

提供明确的刷新/重试路径。恢复连接不得自动重放变更、连接、删除或发布操作。超时后无法确认写入结果时，显示“结果待确认”并利用已有 operation/status 查询核实，不能盲目重试产生重复副作用。

- 节点与组：可区分高亮项、已保存目标和运行目标；删除含混的 Selected 文案，使用清晰文本而非仅靠符号/颜色。
- Nodes 的连接动作若针对高亮项而 Overview 针对已保存目标，必须在动作名称/参数与反馈中明确目标区别；涉及保存的组合动作不能伪装成无其他副作用的同名动作。
- 原生模块：保留 15 个入口、未知字段和原生类型、included 状态、Source/Runtime 区分、Visual/JSON 和外部编辑器。routing 的 p 只在 routing Source Content 生效。不能以表单不支持为由丢字段。
- Logs/统计：保留暂停、有界缓冲、丢弃/截断提示、真实指标与 unavailable；阅览动作不影响核心。
- Config：清楚区分 XRM 设置、核心/资源管理与 Xray 原生 Modules，不通过改 CLI 的已有 config 语义强行统一名称。

普通用户任务不得靠退出 TUI 再发命令才能完成。确实适合 CLI 的高级导出/调试能力可以保留，但要在任务映射中说明，并给出真实、完整、带正确目标/socket 上下文的命令，不凭空添加不存在的选项。

终端布局要求：

- 主体优先呈现当前任务的数据、字段与结果，不用巨量帮助、状态、路径或装饰框挤掉业务内容。
- 全局状态、焦点/模式、路径、通知和上下文帮助保留在底部；错误细节可由就地校验或独立详情层展开，不把整段系统诊断塞进普通列表。
- 80×24 是可操作基线。采用字段优先级、紧凑文案、合理分行和详情展开，不靠截断整句解决所有问题；Ctrl-S 等完整键名和关键动作不得显示为 Ctrl-…。
- 长路径可按语义省略，但要有查看完整路径的明确入口；不可截断机器可引用的输出 ID。
- 内容丰富时合理滚动和渐进展开；宽屏展示更多信息，小屏不丢功能。小于最低尺寸时保护输入，恢复后保留对象、焦点和草稿。
- 统一间距、对齐、强调、表格列、状态词和用语。默认不要求 Nerd Font，不依赖 emoji、颜色或动画才能理解和操作。
- 动效只用于有意义的忙碌/刷新反馈；不增加阻塞按键、延迟完成或持续跳动的装饰动画。

## 八、重设计 CLI 交互和输出，而非包装后端 JSON

保留既有命令名称、有效调用方式、显式 Profile ref、精确名称/UUID、--socket、--json 和可引用 ID。只为明确缺失的正常任务增加命令；优先复用现有 RPC。例如 Profile 的复制、重命名、移除需要按任务矩阵核对是否补齐，不能假定现有 CLI 已支持。

保持默认非交互。错误参数通过 help/诊断和退出码表达；不要新增隐式当前 Profile、要求 TTY 的问答或脚本中的确认等待。新破坏性操作需要明确目标和合理防误用，但不得偷偷改变已有脚本的确认协议。

在人类输出层统一：

- 列表：能识别对象、关键状态和后续可引用标识；空结果清楚，但不污染兼容的机器/管道输出。
- 详情：先给决策必要信息，再给高级字段；不要把原始 RPC JSON dump 当成默认详情设计。
- 变更回执：说明对哪个对象做了什么、结果与作用范围；profile create 至少让用户直接获得名称/ID，connect/disconnect 明确已确认的运行结果，不再默认完全静默。
- 状态：全局 runtime 状态与某个 Profile 的已保存内容有不同作用域。无活动 Profile 时不把 saved_target:null 展示成“所有方案没有保存目标”；优先用现有查询明确解释，新入口如有必要必须真实实现及测试。
- 错误：说明动作、对象、失败原因和可执行恢复方式；服务不可达说明实际连接端点，不能生成未经核实的 systemctl 操作建议。
- 成功回执只报告已确认事实；查询附加详情失败不能把已经成功的写入误报为“未执行”，也不能假称核心启动就代表代理可用。

机器输出兼容单独保护：

- 正常 --json 继续按既有约定输出单行 JSON；stats --watch 保留逐条 JSON 记录，不能加入标题、提示或重绘转义。
- 保留已承诺的字段、类型、错误流和退出码，不因人类输出改版擅自改 JSON schema 或合并 stdout/stderr。
- 进度/诊断与结果分离；非 TTY 不输出动画和屏幕控制序列。尊重颜色关闭需求，对 stdout/stderr 分别考虑输出目标。
- watch 与 Ctrl-C、daemon 中途断开、慢响应应有明确定义和测试；不要仅凭日志文本判断退出成功。
- 默认人类输出与帮助不得泄漏凭据；不要把带秘密的 URL 放进可复制命令。既有明确授权的原始导出/机器接口如有不同契约，应单独核对，不能以脱敏为由静默破坏它。

输出格式变化要有变更说明和回归测试。需要兼容的旧参数顺序继续支持；新增便利写法必须验证，不把报告中的某次参数错误直接当作应修改的后端缺陷。

## 九、分阶段实现，避免半套新交互叠着半套旧交互

阶段 1：可信基线、工具安装/生效证据、统一交互契约与项目 Skill。不要在这阶段结束整个任务。

阶段 2：公共动作分发、焦点/编辑上下文、状态与草稿生命周期。优先解除 I-01 隐藏运行操作、I-11 丢稿、I-03 假空库存、I-02 关键 CLI 静默成功；修复要进入统一设计，而不是增加散落特判。

阶段 3：先打通一个完整纵向任务：Profile 查看/Use/编辑 → 模块或目标保存 → 显式连接 → 状态/日志 → 停止。然后完成订阅生命周期、其他页面和必要 CLI 缺口，统一信息呈现与错误恢复。

阶段 4：终端布局、完整 CLI 输出、跨页/跨端一致性、全量相关回归、真实核心与人工验收交付。

允许拆分 app.cpp/print.cpp 以分离状态、动作、页面、编辑器、输出格式化；不要仅按行数拆文件，不为重构创建新产品框架。CLI/TUI 可以共享领域查询、动作语义和结果模型，但 TUI 不调用 CLI 命令字符串/解析 CLI 文本来驱动自身。

尽量不改 xrmd。确有接口不足时先证明已有接口无法完成任务，做最小兼容扩展并加合同测试；不能让“保护后端”变成伪造 UI 能力的借口，也不能为修前端顺带重写后端。

每阶段都构建并跑对应测试。跨阶段未完成项如实跟踪；不得留下同一页面两套可生效的事件系统再宣布迁移完成。

## 十、验收必须同时观察屏幕和事实

测试分三层：状态/动作/编辑器单元测试；固定尺寸当前格/样式检查；少量覆盖完整任务的隔离 PTY 集成测试。复用现有 tmux、Catch2、CLI/RPC 和 fake-core 基础，不因装了 MCP 重写全部测试基础设施。

MCP 用于 Agent 实际操作和观察；回归测试必须能通过仓库命令重复执行，不能只留在一段不可复现的聊天调用中。

至少落实以下验收矩阵：

T1 焦点与副作用：逐页、逐层、输入框和弹窗验证 Enter/Esc 消费；不合法的 c/d/u/e/p 等不得产生写入或生命周期 RPC。Logs 的 c/d 必须无运行副作用；Profiles 的复制/删除只做其自身动作。除屏幕外检查持久状态、操作记录及 PID/运行状态，不能只看 PID 未变。

T2 Profile：View/Use/Edit/Save 目标正确；Edit 打开真实编辑内容；查看/使用/保存不隐式运行；不同 Profile 分别处于运行、选用、查看和编辑时没有串写。保存/取消结果可见。

T3 草稿恢复：模块、节点、组、Profile、订阅分别覆盖非法输入、服务拒绝、断连和离开；失败保留原稿，成功才更新基线，取消语义一致。至少重现并修复 I-11 的真实 PTY 路径。

T4 原生配置：15 个模块可达，disabled/无 source 可正确处理，Source/Runtime 区分，F2 共用草稿，未支持/未知原生字段不丢失；routing p 只在合法上下文生效。

T5 同进程 resize：带未保存修改完成 80×24 → 120×40 → 70×20 → 80×24，验证草稿/焦点/对象/滚动恢复；80 列关键键名完整，完整路径有可达入口。不得用重新启动另一进程代替。

T6 离线/恢复：首次启动 daemon 不可达和会话中断开分别验证；空库存与未知区分，缓存有过期标识，重连不抢焦点、不丢稿、不自动重放写入。

T7 订阅任务：用本地 HTTP fixture 完成添加、更新、编辑、暂停/恢复、绑定、移除及失败恢复；多 Profile 引用影响明确；不触碰真实订阅、不隐式发布运行文件。

T8 CLI：代表性列表、详情、创建、保存、连接、停止、错误、无结果；分别捕获 stdout/stderr/退出码，覆盖 TTY、非 TTY、--json、watch/Ctrl-C。检查人类回执和机器 schema/参数兼容。

T9 CLI/TUI 一致性：一端保存另一端查询应得到相同领域事实；会话 Use 不是全局持久选择，查询全局 runtime 也不是查询任意 Profile。允许表现形式不同，不允许业务含义相反。

T10 信息与压力：中文、长名称/路径、大列表、异步响应、日志暂停/丢弃提示、统计 unavailable/零/过期区分。保留既有大列表和 Unicode 测试，补本轮布局相关回归。

T11 完整任务：普通用户从资源准备到运行、观察、失败恢复、停止能在设计路径内完成；按实际 help/底部提示走一遍，不依赖作者记得的隐藏键。另外按新人工验收说明走查一次，避免 I-09 再出现。

T12 真实核心：fake-core 只能证明参数/进程/编排，不证明原生配置接受度或代理流量。有可用且获准的真实 Xray 时固定版本/摘要，在隔离 loopback fixture 下验证配置和请求。需要配置依据时读取 https://xtls.github.io/llms-full.txt 的相关内容，不编造字段。没有真实核心或网络/权限受限时明确 BLOCKED/SKIP，不能用 fake-core 代签。

测试以状态条件和有界等待为主，不堆固定 sleep，也不把旧输出出现过一次当通过。发现环境禁止 UDS/PTY 时区分环境失败和产品失败，不通过放宽安全策略伪造绿色结果。

不得删除失败测试、降低断言或重录所有快照来掩盖回归。有意修改旧交互需要给出规范依据；机器契约和领域不变量继续验证。

## 十一、交付内容与完成定义

最终交付实际源码、测试、必要文档、已安装工具记录和项目 Skill，而不是只有设计文档。文档保持少量且有唯一责任：一份权威交互契约、一份执行/验收记录、更新后的使用/人工验收说明即可；如已有合适文件就更新，不大量新增重复规范。

执行/验收记录至少包含：

- 工具来源、版本/commit、实际安装路径、配置修改范围、真实调用证据、仍待重新加载的项目。
- 当前源码/构建产物与测试命令；通过、失败、未运行、受阻分别列出。
- I-01 等审计问题逐项对应的新行为、实现位置、测试和运行证据，不以“代码已改”代替修复证明。
- 关键页面在 80×24/120×40 的真实当前格、必要样式信息和完整任务按键轨迹；CLI 的真实 stdout/stderr/退出码样本。
- 命令兼容性、机器输出兼容性、保留能力、仍存在的接口限制。
- 一份用户能照着操作的人工验收步骤，只使用当前真实可用的键与命令。

完成前自查：

1. 是否仍有执行却未在当前上下文发现的副作用？
2. 是否仍有只显示标签而没有真实流程的功能？
3. 是否能在任意关键页面判断对象、状态、动作和结果？
4. 是否还有失败丢稿、未知装成空值、保存装成运行成功？
5. 是否只是修了审计条目，却没有把普通任务和信息呈现重新组织好？
6. 是否用“安装了 Skill/MCP”“编译通过”“测试字数很多”冒充产品可用？

最终向用户说明实际完成的交互变化、如何体验、验证证据和剩余阻碍。工程自动验收与用户 G5 人工验收分开报告；后者仍由用户复验，不能代签。

现在从读取完整审计、确认当前工作树和宿主能力开始，随后按上述阶段安装、设计、实现并验证。
